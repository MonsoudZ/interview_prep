# Idempotent Inventory Checkout

Mobile clients retry after losing a response. Implement POST /orders so a retry does not create another order or reduce stock twice. The existing controller is a stub; schema and models are provided.

## Contract
A fictional trusted gateway supplies X-Customer-ID as a positive decimal integer. Missing/malformed identity returns 401. No customer table or real authentication implementation is needed. Idempotency-Key is required, 1–64 ASCII letters/digits/underscore/hyphen, otherwise 400.

JSON input: `{ "order": { "product_id": 1, "quantity": 2 } }`. Both fields must be positive JSON integers; strings/floats/booleans are invalid. Missing/wrong-shaped input returns 422. Ignore unknown attributes.

On first success, create one Order and decrease Product.stock by quantity in one database transaction. Return 201 with exactly id, customer_id, product_id, quantity. Product IDs are generated by fixtures. Missing products return 404; insufficient stock returns 409 and inserts nothing. Stock must never become negative.

The key is scoped to customer_id. A repeat with the same key and identical validated product_id/quantity returns the original body with 200 and performs no further stock update, even if stock is now insufficient. Reusing a key with different valid order fields returns 409. Two customers may use the same key independently. Invalid/failed requests must not reserve a key: retrying after replenishment may succeed.

Store the key on the order. Enforce unique (customer_id, idempotency_key) in the database, plus stock >= 0 and quantity > 0 database check constraints. The schema is editable. Preparation recreates the test database. Sequential retries, rollback, and database constraints are executable requirements. Live concurrent requests under SQLite are a discussion follow-up; do not claim these tests establish a production concurrency guarantee.

All failures use JSON `{ "errors": { "base": ["message"] } }` or field errors with nonempty arrays; wording is flexible. A simulated Order.create! failure in tests must propagate while the stock decrement rolls back. Do not swallow unexpected infrastructure errors as client validation errors.

## Time and handoff
65 minutes. First establish one success path, then replay, then conflict/rollback. Explain the transaction boundary, database protections, and what would need changing for a PostgreSQL deployment with concurrent clients.

## Out of scope
Payments, pricing, shipping, external services, order cancellation, and production identity management.
