# Local reviewer evaluation

Run from the repository root with Ollama and the native Rails dependencies available:

```sh
python3 services/review_worker/evaluate.py --output artifacts/reviewer-evaluation/run-001
```

The output directory must be new. Use `--case lru-cache-reference` to select one case. Add `--thinking` to evaluate reasoning mode (the production default, including its fall back to the fast setting when the reasoning budget is exhausted, recorded as `reasoning: 0` in usage) or omit it for the fast setting; `--rescore` re-applies the semantic checks to an existing output directory without inference; `--repeats N` reviews each case N times (see below). No Linux worker is needed. The harness builds packets from published Ruby and Rails exercises, an author-written design note, and the production guidance selector, invokes the real local provider, and validates each result with the actual Rails report validator. It never creates accounts, submissions, or ratings. Output contains the exact packet, model digest, prompt digest/version, raw report, usage, and contract-validation result.

Contract success is not a semantic pass. Each case also carries author-specified expectations that the harness checks automatically and records under `semantic` in each report and in `summary.json`: `missed_defect` and `defect_uncited` for planted defects, `leaked_criteria` when a defect lowers an independent source criterion, `unsupported_downgrades` and `unsupported_major_findings` for reference solutions, `process_criteria_rated` when a criterion about the candidate's explanation is rated without any transcript, and `execution_observations_without_runs`. Every flag is a separate failure mode. The exit status is non-zero when any report is invalid or any flag is set. The flags cover only the planted expectations; read the full reports against this table:

| Case | Expected behavior |
| --- | --- |
| LRU reference | Accept insertion-ordered Hash as a valid solution. No mandatory linked list; no invented correctness issues. Missing logs alone cannot reduce source ratings. `get` returning `nil` for both a stored `nil` and an absent key is the published contract (exercise version 2 says so in the brief and the `boundaries` probe); demanding a sentinel is an unsupported downgrade. |
| LRU defect | Identify that `get` fails to refresh recency, with a valid source citation and failing sequence. Do not claim that this makes the operation slower than O(1). `complexity` and `boundaries` stay independent: the mutation changes neither the cost of an operation nor how a stored `nil` is kept, counted or returned. The `boundaries` target deliberately leaves recency refresh to `correctness`; a first draft of version 2 said a stored `nil` is "refreshed by `get`" and the model then lowered `boundaries` for the planted defect in two of two reasoning attempts, which was a correct reading of overlapping criteria, not a leak. |
| Rate limiter reference | Accept the stated single-process contract. No Redis, distributed locking, or multi-server requirement from the separate follow-up. |
| Rate limiter defect | Detect incorrect expiry at the exact boundary: with limit 1/window 10, an accepted request at time 0 must not block time 10. |
| Tenant projects reference | Accept the published controller: Bearer-token authentication, lookups scoped through the authenticated user's organization, ownership resolved before the role check, and a validated name as the only assignable attribute. No added revocation, membership, constraint, or OAuth requirement from the follow-up. The submission is the editable starter files with the repaired controller; absent tests or logs cannot reduce source ratings. |

These are development regression cases, not a held-out benchmark or human-calibrated scoring set. The LRU cases were already used to improve the prompt. The rate-limiter pair is an initial transfer check; future tuning on it makes it a regression example too. The tenant-projects pair is the first Rails-track case; it checks a multi-file submission whose defect is a published-requirement contradiction rather than a style preference. Its first two reasoning-mode attempts (2026-10-25) both found and cited the planted line and both lowered `authorization` for the viewer 403-instead-of-404 consequence described above, which is why that criterion is no longer listed as independent for the defect variant.

## Calibration decisions

Two recurring flags turned out to be problems with the published text or the fixture, not with the reviewer:

- **LRU `boundaries` leak (prompt versions v5 to v9, fast and reasoning).** Version 1 of the brief said `get` "returns the stored value, or `nil` when absent" and "A stored `nil` is a real entry", and the `boundaries` probe asked why `get` must distinguish a stored `nil` from an absent key. The reference returns `nil` in both cases and no visible or supplemental test asks for anything else: the `nil` group checks that a stored `nil` occupies a slot and appears in `keys`, and the oracle compares `get` results, recency order and size. A reader, model or human, could take the probe as a contract on the return value and demand a sentinel, so the model's reading was a defensible one of ambiguous text rather than an error. Exercise version 2 (brief, `boundaries` target, probe and practice; `ruby-lru-cache-review-v2`) states that callers cannot tell the two apart through `get`, that this is the contract and not a gap, and that only the implementation must distinguish them so a stored `nil` is kept, counted and refreshed. Tests, reference and the `ruby.lru-cache.v1` operation are unchanged, so no sandbox image rebuild is needed. The evaluator builds its LRU packets from the current manifest and therefore now reviews against version 2; version 1 is archived under `curriculum/ruby/lru-cache/versions/1/` for sessions created on it. Live check on 2026-10-26 (reasoning mode, two attempts per case): the reference stayed clean and the sentinel demand did not appear in any attempt; after the `boundaries` target was changed to leave recency to `correctness`, both defect attempts found and cited the defect with no leaked criteria (one was rejected by the contract for a 27-line citation). See `deploy/studio/VERIFICATION.md`.
- **Tenant projects `authorization` leak.** Kept the planted line (it is the exercise's defining defect and the only one that contradicts a quoted sentence of the brief) and removed `authorization` from the defect case's independent criteria, for the reason in the table. Choosing a different line whose consequence stays inside one criterion was considered and rejected: every scoped-lookup mutation also changes the viewer's status path, and a role-check or name-validation mutation would test a different, weaker reading of the exercise. Track missed defects, unsupported findings, criterion leakage, and latency separately. Do not turn schema-valid reports into an accuracy percentage.

## Repeated runs

The same packet at temperature 0 has produced different leakage flags on consecutive runs, so one run cannot confirm that a prompt change helped or hurt. `--repeats N` reviews every selected case N times and stores each attempt as `case.1.json`, `case.2.json`, and so on, each a complete record with its own report, usage, contract validation, and semantic flags. With `--repeats 1` (the default) the output keeps the single-run shape: one `case.json` per case and one flat entry per case in `summary.json`.

With N above 1 each case's entry in `summary.json` records agreement across attempts rather than a single verdict: `attempts` (how many ran), `clean_attempts` (valid report and no flag set), `invalid_attempts` (rejected by the report validator or an inference error; these count as neither clean nor flagged), `flag_attempts` (each flag that was ever set, with the number of attempts in which it was set), and `results` (the per-attempt summaries in order). The exit status is non-zero unless every attempt of every case is clean. `--rescore` recognizes both naming schemes, re-checks every attempt file, and rebuilds the same aggregate entries; `summary.json` is rewritten after each case so a run interrupted mid-way still leaves a readable partial summary.

The aggregate is deliberately counts only. A clean fraction over three or five attempts would read as a precision figure while really being a small-sample repeatability observation on author-planted defects, and averaging distinct failure modes (a missed defect, a leaked criterion, a fabricated execution observation) into one number hides which one moved. Compare a prompt change by reading which flags appeared in how many attempts before and after, with the same model digest and repeat count.
